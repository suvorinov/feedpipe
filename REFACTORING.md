# Предложения по рефакторингу Feedpipe

## Обзор функционала "Входящие" - "Отложенные"

Текущая логика:
- `status='inbox'` — новые/непрочитанные статьи
- `status='later'` — отложенные статьи
- `status='archived'` — удалённые статьи

---

## Проблемы и предложения

### 1. API статьей (app/main.py)

**Проблема:** API для работы со статьями разнесено по разным роутам, нет единообразия.

| Роут | Метод | Описание |
|------|-------|----------|
| `/api/articles/{id}` | DELETE | Архивирование (purge) |
| `/api/articles/{id}/hold` | PATCH | Отложить в later |
| `/api/articles/{id}/restore` | PATCH | Нет (вернуть из later в inbox) |

**Предложение:**
```python
# Унифицировать API
@app.patch("/api/articles/{article_id}/status")
def update_article_status(article_id: int, status: str):
    # status: "inbox" | "later" | "archived"
```

---

### 2. Отсутствует функционал "Вернуть"

**Проблема:** Статью можно отправить в "Отложенные", но вернуть обратно во "Входящие" — нет.

**Предложение:** Добавить кнопку "вернуть" на странице "Отложенные":
```html
<button hx-patch="/api/articles/{{ article.id }}/restore" ...>
```

---

### 3. Счётчики в реальном времени

**Проблема:** После действий (удалить/отложить) счётчики обновляются только на главной странице, но не синхронизируются между вкладками.

**Предложение:** Использовать WebSocket для broadcast изменений счётчиков:
```python
await manager.broadcast({
    "type": "counter_update",
    "inbox_count": new_inbox,
    "later_count": new_later
})
```

---

### 4. Индексы БД

**Проблема:** Нет индексов для часто используемых запросов.

**Предложение (db.py):**
```python
cursor.execute('CREATE INDEX IF NOT EXISTS idx_articles_status ON articles(status)')
cursor.execute('CREATE INDEX IF NOT EXISTS idx_articles_source ON articles(source_url)')
```

---

### 5. Бесконечная прокрутка (lazy load)

**Проблема:** Реализована, но:
- `offset` + `limit` — неэффективно для больших БД
- Нет проверки "все ли загружены"

**Предложение:**
- Использовать cursor-based pagination (по ID)
- Или переключить на offset-based, но с кнопкой "Загрузить ещё"

---

### 6. Разделение логики парсера и API

**Проблема:** `parser.py` содержит и парсинг, и работу с БД.

**Предложение:** Разделить на слои:
```
app/
  parser/
    fetcher.py   # получение фидов
    parser.py    # парсинг RSS/Atom
    storage.py   # сохранение в БД
```

---

### 7. Обработка ошибок парсинга

**Проблема:** Ошибки парсинга отдельных фидов не логируются структурированно.

**Предложение:**
- Вести лог проблемных фидов
- Добавить метрику "последний успешный парсинг" для каждого фида

---

### 8. Код состояния при архивировании

**Проблема:** При успешном действии возвращается пустой `HTMLResponse(content="", status_code=200)`.

**Предложение:** Возвращать HTMX-шаблон для плавного обновления или использовать `204 No Content`.

---

### 9. Безопасность

**Проблема:** Нет проверки авторизации, приложение полностью открыто.

**Предложение:** Добавить базовую auth (если планируется публичный доступ).

---

### 10. Тестирование

**Проблема:** Нет тестов.

**Предложение:** Добавить pytest с фикстурами для БД и парсинга.

---

## Приоритеты

1. **Высокий:** Индексы БД, функционал "вернуть", исправление счётчиков
2. **Средний:** Рефакторинг API, lazy load
3. **Низкий:** Слои парсера, тестирование, auth
