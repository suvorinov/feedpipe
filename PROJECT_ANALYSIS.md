## 1. Коротко о проекте

**Feedpipe** — персональный RSS/Atom-агрегатор в «бруталистском» терминальном стиле.
Один пользователь, один сервер, SQLite — по-хорошему компактная штука.

- **Backend**: Python 3.11, FastAPI, SQLite (raw `sqlite3`, без ORM), APScheduler, httpx, feedparser, bcrypt
- **Frontend**: серверный рендеринг Jinja2 + **htmx** (2.0) + немного ванильного JS + WebSocket
- **Расширение**: Chrome MV3 «Feedpipe Injector» (добавить текущий сайт в подписки)
- **Деплой**: Docker + Nginx Proxy Manager (общая сеть), GitHub Actions CI

Стек выбран грамотно: никакого SPA-монстра ради персонального RSS-ридера. htmx + серверный
рендеринг — это ровно KISS, о котором мы с тобой любим говорить.

```
Клиент (браузер / расширение)
   │  HTTP/htmx + WebSocket(/ws)
   ▼
FastAPI (app/main.py) ──── CSRF-guard ──── /health
   ├── routers/        (web, articles, feeds, auth, sync) — HTTP-слой
   ├── repositories/   (articles, feeds, users) — работа с SQLite
   ├── parser.py       (фид-парсинг: feedparser + httpx, semaphore)
   ├── sync_state.py   (оркестрация синка + статусы + broadcast)
   ├── ws_manager.py   (рассылка сообщений по WebSocket)
   ├── auth.py         (HMAC-сессии, bcrypt, лимит попыток)
   └── db.py           (схема, WAL, write_lock, регистрация адаптеров)
SQLite (articles / feeds / users)
```

## 2. Что сделано сильно (честно — молодцом)

### Безопасность — уровень, которого нет у 90% хобби-проектов
- **CSRF-мидлварь** с проверкой Origin/Referer на изменяющих методах, плюс пропуск для
  `X-Feedpipe-Session` (расширение) и клиентов без Origin (curl). Продумано и задокументировано.
- **SSRF-защита**: проверка и IP-литералов, и DNS-резолва каждого адреса, **и** итогового URL
  после редиректов (redirect — классический обход фильтра). Список приватных сетей полный.
  Это редкая внимательность. `app/routers/feeds.py:50`
- **Сессии**: HMAC-SHA256 подпись, `compare_digest` (без timing-атак), секрет в файле с
  `O_EXCL` + `0o600` (защита от гонки двух процессов), `HttpOnly` + `SameSite=Lax`.
- **Пароли**: bcrypt, битый хэш не роняет проверку.
- **Брутфорс**: rate-limit по IP с очисткой окна (in-memory — ок для одного сервера).

### Архитектурные решения
- **Keyset-пагинация по id** вместо `OFFSET` — стабильная и быстрая на больших таблицах.
  Берём `limit+1` записей, чтобы узнать `has_more`. Чисто.
- **Сериализация записи** через `write_lock` (RLock) + WAL: «database is locked» лечится на
  уровне процесса, а не на коленке. `app/db.py:24`
- **Не блокируем event loop**: `asyncio.to_thread` для sqlite-вызовов и `getaddrinfo`,
  `run_coroutine_threadsafe` для моста APScheduler → главный loop. Мелочь, но кто это
  делает в персональных проектах?
- **Ретраи вставки** при блокировке БД с экспоненциальной паузой (`save_articles`).
- **`total_changes` для подсчёта реально вставленных** при `INSERT OR IGNORE` — аккуратный трюк.
- **Дедупликация статей по `link UNIQUE`** — просто и надёжно.
- **Автоочистка архива** (ночная джоба, retention 90 дней) — не даёт базе пухнуть вечно.
- **Удаление фида каскадом удаляет его статьи** — не разбрасываемся мусором.

### Тесты
115 тестов, все зелёные, и покрытие приятное: юнит (парсер, фильтры, auth), интеграционные
(flow: добавить фид → синк → отложить → удалить), безопасность (CSRF, SSRF, подделка cookie),
WebSocket, пагинация, гонка записи через потоки. Подмена HTTP и DNS фикстурами — тесты не ходят
в сеть. Изоляция БД через tmp_path. Это не «тесты ради галочки».

## 3. Проблемы и точки роста

### 🔴 3.1. Утечка sqlite-соединений (реальная, исправить первым делом)

`get_db()` — обычная функция, `Depends(get_db)` вызывается в 8 местах. FastAPI закрывает
только `yield`-зависимости, а тут соединение **никто не закрывает**. Под нагрузкой это
набор не закрытых fd и не закоммиченных транзакций, пока не сработает GC.

Фикс — одна строка по сути: сделать генераторную зависимость:

```python
def get_db():
    conn = sqlite3.connect(...)
    try:
        yield conn
    finally:
        conn.close()
```

### 🔴 3.2. `create_task` без ссылки на задачу (риск «съеденной» задачи)

`app/routers/sync.py:15` — `asyncio.create_task(run_parser_async())` в эндпоинте. Ссылка
никуда не сохраняется; планировщик хранит о тасках только weak-ссылку. Если задача не
завершится за один проход цикла событий и её никто не держит — CPython её соберёт GC,
и синк просто не выполнится. Рекомендация: либо `BackgroundTasks` FastAPI, либо хранить
ссылку (например, в `sync_state`).

### 🟠 3.3. Rate-limit логина «за прокси» бьёт по всем

В `routers/auth.py:66` берётся `request.client.host`. За NPM это IP прокси — значит:
1. лимит фактически один на всех (недобросовестный пользователь может «заморозить» логин всем);
2. сам по себе он обходится тривиально (все запросы уже с одного IP).

Для персонального сервера не критично, но можно дешево улучшить: бакетить по
`X-Forwarded-For` **только** из доверенного прокси, или хотя бы добавить бакет по username.

### 🟠 3.4. Тройное дублирование проверки авторизации

`verify_auth_cookie(cookie) → fallback header` в `auth.get_current_user`, отдельно в
`web.read_root` и отдельно в `websocket_endpoint`. Три копии одной логики. Стоит вынести
в общую функцию/зависимость — меньше шансов разойтись при следующем изменении (например,
когда добавишь `Secure` флаг).

### 🟠 3.5. Cookie без `Secure` и без ограничения `Secure`-сценария

`routers/auth.py:84` — cookie ставится без `secure=True`. Приложение живёт за NPM с TLS,
т.е. браузер видит https, и флаг безопасно добавить. Рекомендую: `secure=True` (или гейт по
настройке), плюс `SAME_SITE` уже на месте. Мелочь, но это «правильная» практика.

### 🟡 3.6. `_load_secret()` читает файл на каждый вызов подписи/проверки

В `auth.py` секрет читается с диска при каждой проверке cookie (каждый запрос — 1–2 чтения).
Для одного сервера — копейки, но кэш в памяти (с инвалидацией по env) уберёт лишний I/O
и упростит рассуждения.

### 🟡 3.7. Глобальное изменяемое состояние `SYNC_STATUS`

`sync_state.py` — глобальный dict + threading.Lock. Работает, но любой будущий рефакторинг
(второй воркер, мультипроцесс, кластер) это сломает. Если хочется KISS и дальше — можно
обернуть в маленький класс-синглтон с методами `start()/finish()`, оставив ту же семантику.

### 🟡 3.8. Смешение ролей в `parser.py`

`app/parser.py` — и библиотека (функции для синка), и CLI-скрипт (`__main__` → `main()`).
Функция `main()` делает всё: init_db, миграции, сборку, сохранение, логирование. Из-за этого
`sync_state` импортирует `main` и прогоняет «скрипт внутри приложения». ОК для масштаба,
но разделение на `sync()` (логика) и `main()` (обёртка CLI) уберёт путаницу и сделает
тестируемость ещё проще.

### 🟡 3.9. Дублирование HTTP-загрузки

`parser.fetch_feed` и `routers/feeds._fetch_page` почти одинаково ходят по сети (разные
клиенты, заголовки, таймауты). Плюс `_fetch_page` создаёт новый `httpx.AsyncClient` на каждый
вызов (2 клиента на одно добавление фида). Один общий модуль `http_client` с переиспользуемым
клиентом уберёт дубль и даст единую точку для таймаутов/юзер-агента.

### 🟡 3.10. Фид-дискавери — хрупкая эвристика и regex по HTML

- `if not url.endswith(".xml") ... and "feed" not in url` — признак «возможно фид» по подстроке
  `feed` в URL. Сайт `foodblog.example` с настоящим `/rss.xml` попадёт в ветку discovery и
  может зафейлиться зря (впрочем, там есть fallback).
- Regex по HTML для поиска `<link rel="alternate" type="application/rss+xml">` не покрывает
  все реальные варианты атрибутов (порядок, одинарные/двойные кавычки, `application/atom+xml`
  уже есть). Для персонального ридера достаточно, но `html.parser` из stdlib был бы надёжнее.

### 🟡 3.11. `TEMPLATES_DIR = "templates"` — относительный путь

`template_filters.py:6` зависит от текущей рабочей директории. В Docker `WORKDIR=/app` —
работает, локально из корня репо — работает, но это хрупко. Правильно — резолвить от
`Path(__file__).parent.parent`, как это уже сделано для `STATIC_DIR` в `main.py`.

### 🟢 3.12. Схема БД: ссылки по `source_url`, а не по FK

`articles.source_url` — строка, а не `feed_id` с внешним ключом. Каскад при удалении фида
сделан вручную (`DELETE FROM articles WHERE source_url = ?`). Работает, и для текущего
масштаба нормально. Если фид сменит URL (нормальная жизнь RSS), статьи «осиротеют» —
уже с индекса на source_url это легко гуглится, но FK избавил бы от ручной магии.

### 🟢 3.13. Мелочи и гигиена

- `python-dotenv` и `PyYAML` в `requirements.txt` **нигде не используются** — убрать (в том
  числе меньше копируемого в контейнер).
- **Нет `.dockerignore`** → в build context попадают `.venv/`, `.git/`, `data/` (с `secret.key`!).
  Сами `COPY` в Dockerfile их не берут, но контекст раздувается, а риск случайной утечки
  секрета в образ не нулевой. Добавить `.dockerignore` обязательно.
- README: раздел «Структура» устарел (не упоминает `routers/`, `repositories/`, `sync_state`,
  `ws_manager`). Обновить — гайд, по которому новичок (и будущий ты) ориентируется.
- `manifest.json` лежит в `app/`, отдаётся через `FileResponse`; PWA заявлен, но
  service worker'а нет — без него «standalone» и иконки работают не на всех платформах.
- `style.css?v=4` — ручной cache-busting; рано или поздно забудешь обновить цифру.
- `run.sh` и Makefile дублируют запуск — не беда, но можно оставить один источник.

## 4. Что бы я сделал следующим (приоритетный список)

1. **`get_db` → yield-зависимость** с `finally: conn.close()` — закрыть утечку (3.1).
2. **Не терять ссылку на задачу синка** в `/api/sync` (3.2).
3. **Добавить `.dockerignore`** — маленький, но важный для безопасности/размера образа.
4. **Убрать мёртвые зависимости** `python-dotenv`, `PyYAML`.
5. **Вынести авторизацию** в единую зависимость (3.4) + `secure` флаг cookie (3.5).
6. Обновить README-структуру (3.13).
7. По желанию: общий HTTP-модуль, кэш секрета, класс для `SYNC_STATUS`, `Path(__file__)`
   для шаблонов.

Пункты 1–2 — единственные, которые я бы назвал «надо исправить». Всё остальное — полировка.

## 5. Вердикт

Для персонального проекта уровень **высокий**. Код хорошо структурирован, откомментирован
именно там, где нужен WHY, а не пересказ WHAT. Безопасность продумана на порядок глубже
среднестатистического сервиса. Тесты реально тестируют, а не горят зелёным.

KISS соблюдён: никакого переусложнения, ORM не натянут, микросервисы не «наклеены» ради моды.
Главные претензии — утечка соединений и пара фригольных async-моментов, которые лечатся
буквально за полчаса.

**Оценка: 8.5/10.** До девятки — пункты из секции 4.1 и 4.2.
